# 架构与维护说明

## 设计目标

这套代码是最终主线。它刻意保留一条业务路径、一个配置入口和一组稳定数据类型，避免旧项目中视觉、机械臂 SDK、槽位编号和任务流程互相调用。

五条不可破坏的边界是：

1. `agent` 只把文本变成一个经过确定性校验的 `TransferCommand`，不接触硬件。
2. `vision` 只把一帧 RGB-D 和拍摄时右臂位姿变成 `RackObservation`。
3. `workflow` 只根据槽位状态决定抓哪里、放哪里，以及动作顺序。
4. `motion` 只接收 `Point3D`、`Pose6D` 和数值参数，不允许读取 YOLO、rack、row、column 或 SDK。
5. `hardware` 只完成接口到设备 SDK 的翻译，不允许决定业务目标。

项目没有 AprilTag、分割模型、语音识别、导航或双臂协同的隐藏支路。Gemini 是可选文本适配器，默认离线模式不需要网络或 API。

## 模块职责

| 位置 | 唯一职责 | 什么时候修改 |
|---|---|---|
| `config/app.yaml` | 相机、右臂、夹爪、视觉阈值、几何量和运动限值 | 实验标定或更换设备参数 |
| `config/hand_eye.yaml` | `camera → right flange` 的 4×4 齐次变换，平移单位 mm | 重新手眼标定 |
| `config/poses.yaml` | 观测位和竖直工具姿态 | 重新示教固定观测位 |
| `core/models.py` | 跨模块共享的不可变对象和单位约定 | 数据契约真的发生变化时 |
| `core/ports.py` | 相机、检测器、机械臂、夹爪最小接口 | 接入同类新硬件时 |
| `agent/` | 文本到 `TransferCommand`；本地解析或 Gemini 手动函数调用 | 更换语言模型或命令表达时 |
| `hardware/` | D435、RealMan、RM Plus 的实际调用 | 厂商 SDK 版本或硬件变化时 |
| `vision/` | 检测、K0、网格、深度、手眼变换 | 改识别算法或相机几何时 |
| `motion/planner.py` | TCP 目标到竖直法兰航点的纯计算 | 改运动策略时 |
| `motion/executor.py` | 全计划检查后逐点发送，并在异常时停止 | 改安全限值或发送策略时 |
| `workflow/manipulation.py` | 源/目标状态检查和抓放顺序 | 改任务规则时 |
| `app.py` | 从同一份 YAML 组装 fake 或 real 实现 | 增减正式组件时 |
| `cli.py` | 操作者入口、确认门和诊断输出 | 增加正式运维命令时 |

日常调参优先修改 YAML，不要把实验室坐标和阈值写回 Python。

## 稳定数据契约

- `Pixel(u, v)`：彩色图像素坐标。
- `Point3D(x_mm, y_mm, z_mm, frame="base_right")`：右臂基坐标系三维点。
- `Pose6D(..., rx_rad, ry_rad, rz_rad)`：位置 mm、欧拉角 rad。
- `SlotAddress(rack_id, row, column)`：严格 2×6，文本形式为 `rack_1.r2c6`。
- `SlotObservation`：一个槽位的 `EMPTY/OCCUPIED`、置信度、像素中心和可用三维点。
- `RackObservation`：一个机架恰好 12 个不重复且完整的槽位、K0 和架面 Z。
- `TransferCommand(source, destination)`：未来语音模块也必须输出这一对象。
- `MotionPlan`：一个或多个带速度和 `LIN/J_P` 类型的法兰 `Waypoint`。

全项目计算单位是 mm + rad。`RealManArm` 是唯一进行 mm ↔ m 转换的位置；不要在其他模块再次除以或乘以 1000。

## 一次扫描发生什么

1. 程序确认右臂在已确认的观测位。
2. 读取曝光前后的右臂位姿；拍摄期间平移超过 0.5 mm 或转动超过 0.2°就拒绝该帧。
3. D435 把深度和彩色图对齐，读取本次真实彩色内参，并把原始深度换成 mm。
4. YOLO 输出 `empty_hole` 和 `tube_cap`，总数必须恰好为 12。
5. HSV 找到当前 rack 约定颜色的近方形 K0 候选；落在任一 YOLO 框内的彩色候选会被排除。
6. 网格模块用检测中心拟合 2×6 仿射网格，只接受位于角点外侧的唯一 K0；零个或多个合格候选都拒绝。K0 确定 `r1c1` 和行列方向，同时检查间距及残差。
7. 对 `tube_cap` 在框中心附近取有效深度，经过内参、手眼矩阵和拍摄位姿变到 `base_right`。
8. 盖顶 Z 必须彼此一致；中位数减去 `cap_top_above_rack_mm` 得到实测架面。若有人工标定，实测值必须与标定相符并使用标定值；全空时必须使用标定值。
9. 对 `empty_hole`，从像素发出相机射线，与水平架面相交得到放置 XY/Z。
10. 输出完整 `RackObservation`，并在开启调试图时保存带槽位编号的图像到 `artifacts/`。

## 一次搬运发生什么

`workflow` 先完成整架扫描，并在夹爪闭合前同时验证：

- 源槽位为 `OCCUPIED` 且有盖顶坐标；
- 目标槽位为 `EMPTY` 且有架面孔坐标；
- 两者属于同一个 rack；
- 从当前位姿到源、抬升、到目标和再次抬升的全部航点都在工作空间内；
- 单段距离、坐标系和工具竖直姿态符合限制。
- 当前法兰仍处于生成这份计划时的起始位姿，不能在打印计划后移动机械臂再执行。
- `MOVE` 后立即复扫，K0、12 个状态、像素、架面和源/目标三维点与打印计划一致。

抓取 TCP 目标为盖顶沿基坐标 Z 向下 5 mm。放置 TCP 高度为：

```text
架面 Z + 试管盖顶高出架面的高度 - 5 mm + seating_adjust_mm
```

运动顺序固定为：张开夹爪 → 安全抬升 → 对齐竖直姿态 → 移到源上方 → 竖直下降 → 夹紧 → 竖直抬高 → 移到目标上方 → 竖直下降 → 释放 → 竖直抬高。

`MotionPlanner` 生成数值航点；`MotionExecutor` 先检查整个计划，再由 `RealManArm` 逐点做阻塞运动。当前机架近场航点全部使用 `rm_movel`，保证法兰端点间走笛卡尔直线；冗余的零距离点不会发送给控制器。每段阻塞运动后都会回读法兰位姿，实际到位误差超限就停止。规划器从不知道源是哪个槽，也不会直接调用硬件。

携管横移前的撤离高度有明确包络约束：

```text
retreat_height_mm >= tube_total_length_mm + required_carried_clearance_mm
```

当前 120 mm 管长来自旧管记录，30 mm 是要求的邻管净空；新管到货后必须重测。修改管长但忘记同步增加撤离高度时，配置组装会直接失败。

## 失败方式是项目的一部分

系统宁可拒绝当前帧，也不猜测槽位。以下情况会直接结束命令，不发送后续运动：模型类别不符、检测数不是 12、K0 不存在/歧义/太远、网格畸变过大、深度无效或盖顶 Z 离群、真机架面未标定、源空、目标有管、坐标越界、姿态不竖直、管长净空不足、计划后机械臂或现场发生变化、控制器非物理模式或未上电、阻塞运动实际未到位。

运动执行异常时软件请求减速停止，但网络断开或控制器故障时软件停止不能替代物理急停。

## Agent 与未来语音

当前 `agent-plan` 已能把文本规范化为现有 `TransferCommand`，例如：

```text
“把一号架第一行第二列移到二号架第二行第六列”
                     ↓
TransferCommand(rack_1.r1c2, rack_2.r2c6)
```

Gemini 使用手动函数调用，SDK 自动函数执行被显式关闭；模型输出还会重新验证字段、rack、整数行列和范围。`agent-plan` 只规划不运动；`agent-transfer` 把验证后的 `TransferCommand` 交给与普通 `transfer` 完全相同的安全执行路径，模型本身仍不能调用硬件函数。未来语音目录只负责语音转文本，再调用同一个 Agent；语音和 Agent 都不得直接调用 workflow、读取相机、生成坐标或控制机械臂。识别不确定时应请求用户复述，而不是猜槽位。具体配置与命令见 [Agent 接入说明](AGENT.md)。

## 未来接入导航和跨架搬运

当前跨架被锁定，因为“夹住试管后移动底盘”至少还缺少：两个站点的导航目标、到站静止判定、右臂安全携带位、底盘运动期间的夹持状态处理、到站后重新观测目标架，以及失败恢复流程。仅仅删除同架检查不是导航实现。

以后增加一个跨站应用层协调器，并在每次机械臂动作前复用当前安全门：

```text
navigate(source rack) → settle → scan → pick
→ arm carry pose → navigate(destination rack) → settle
→ scan → place
```

导航模块只接受 `rack_id` 并报告“到站且静止”；协调器调用现有 `scan/pick/place`。视觉仍输出 `RackObservation`，运动规划仍只接受坐标，所以不需要把导航逻辑塞进视觉或 planner。

## 修改时的最小验证

- 改纯数据或流程：运行全部 `unittest` 和 fake 搬运。
- 改视觉：运行全部视觉测试，再对两个 rack 的保存图像做重复 `scan`。
- 改坐标、手眼或 TCP：除单元测试外，必须重新执行低速真机分阶段检查。
- 改硬件驱动：先运行对应无运动命令，确认 SDK 返回值格式，再进入运动阶段。
- 改模型：先验证类别契约和 exact-12 成功率，不能只看 mAP。
